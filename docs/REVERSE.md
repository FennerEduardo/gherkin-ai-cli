# Reverse engineering: from existing code to specifications (`ghk reverse`, beta)

`ghk reverse` reads a codebase that already runs in production and proposes Gherkin features that describe what it does today. Each proposed step points to the line of code (or the contract, or the test) that supports it. The proposals are a starting point for review. They let a team adopt gherkin-ai on an existing repository without first writing every specification by hand.

> **Status: beta in 3.3.0.** The command, its output files and its JSON shape may still change in a 3.3.x release. The maturity of each analyzer is listed below and in `reverse scan --json`.

## 1. The workflow

```bash
npx gherkin-ai@3 reverse scan                      # evidence → .ghe/reverse/scan.json
npx gherkin-ai@3 reverse propose                   # proposals → .ghe/reverse/proposals/*.feature
npx gherkin-ai@3 reverse coverage                  # how much of the code the existing features specify
# review the proposals, then:
npx gherkin-ai@3 reverse accept order invoice --yes          # → features/discovered/
npx gherkin-ai@3 reverse accept --all --merge --yes          # only what no feature specifies yet
npx gherkin-ai@3 lint --all && npx gherkin-ai@3 converge --all
```

None of the subcommands needs `ghk init` or calls a language model. `scan`, `propose` and `coverage` write nothing outside `.ghe/reverse/`. `accept` writes feature files only after you confirm interactively, or with `--yes`. Without a terminal and without `--yes`, it writes nothing and exits 2.

### accept

`reverse accept <aggregate…>` (or `--all`) writes the reviewed proposals to `features/discovered/<aggregate>.feature` (`--to` changes the directory):
- the `@needs-review` tag is removed;
- `@reverse-engineered @characterization` and every `# evidence:` comment are kept;
- an existing file is not overwritten without `--force`;
- each accept is recorded in the audit log (`reverse:accept`).

With `--merge`, the operations a feature already specifies are left out, and the command exits 7 when a feature declares commands that no operation in the code implements.

### coverage

`reverse coverage` compares every operation in the code with the commands the generator derives from the existing features. Each operation gets one of these statuses:

| Status | Meaning |
|---|---|
| documented | A feature declares the same command (or the same `@query`) |
| renamed | A feature declares the same verb, or a synonym, on a related noun: `CreatePeriod` in the code, `CreateAcademicPeriod` in the feature. The behaviour is specified, but the names drifted |
| undocumented | No feature declares it |
| spec-only | A feature declares a command that no operation in the code implements |

*Behaviour coverage* is the share of operations that are documented or renamed. `--min <pct>` exits 7 below it, so it can gate CI. `propose` prints the same summary.

On the LMS (nine services, read-only), coverage goes from 0% to 50% per service. 16 of the 81 operations in the code are specified: 9 with the same name and 7 renamed. Most of the rest are reads (GET), which the LMS features do not specify.

## 2. What it reads

| Source | What becomes evidence |
|---|---|
| Routes and controllers | HTTP method and path, the handler, the controller or router it belongs to |
| Guards and middleware | Authentication (`@UseGuards`, `requireAuth` middleware, `if (!req.user) return 401`) and roles (`@Roles('manager')`) |
| DTOs and validators | Required fields and rules (class-validator decorators; required properties in an OpenAPI request body) |
| Handler and service bodies | Guarded failures (`if (…) throw new NotFoundException('Order not found')`, `return res.status(422)…`); status values written (`order.status = 'CANCELLED'`); events published (`emit('order.placed')`, `new OrderApprovedEvent()`); persistence calls; the success status. Service methods are followed through the type checker, three levels deep. |
| OpenAPI documents | Operations, `operationId`, documented responses and required request fields. Documents are found under any name containing `openapi` or `swagger`; `--openapi` selects them explicitly. gherkin-ai's own `contracts/` and `generated-specs/` are skipped, because they were derived from the features. |
| Tests | HTTP calls made by tests: supertest, MockMvc, RestAssured, TestClient and httptest. A test that calls an endpoint confirms that endpoint's behaviour. |
| Code generated by gherkin-ai | Generated services expose one dispatcher, `POST <route>/{id}/{command}`. The `ghk-kernel` analyzer reads the aggregate behind it, in every language the kernel is generated in: the command methods, the event each one records, and the literal messages of `assertValid` (returned as 422). Each command becomes its own operation. |

Health probes, metrics and API documentation routes (`/health`, `/actuator/*`, `/metrics`, `/swagger-ui`, `/api-docs`, …) are platform operations, not business ones, and are left out. A generic dispatcher whose commands no analyzer can list becomes an open question.

Discovery never opens these files:
- secret files: `.env*`, `*.pem`, `*.key`, `*secrets*`, `*credentials*`;
- dependencies and build output: `node_modules`, `dist`, `build`, `target`, `vendor`, `bin`, `obj`;
- gherkin-ai's own state;
- anything the repository's `.gitignore` ignores.

Comments and strings in the code are treated as data, never as instructions.

### Configuration

Every option can also be set in the `reverse` section of `gherkin-ai.config.json`. Command-line flags win.

```json
{
  "reverse": {
    "path": "src",
    "include": ["src/**"],
    "exclude": ["src/legacy/**"],
    "openapi": ["docs/openapi.yaml"],
    "tests": true,
    "minConfidence": "strong",
    "threshold": 80,
    "acceptDir": "features/discovered",
    "minCoverage": 60
  }
}
```

### --assist (opt-in)

`reverse propose --assist` asks the configured LLM to word each proposal better. It may propose:
- a feature title;
- a user story (*As a / I want / So that*);
- clearer scenario names.

It cannot add, remove or change steps: its answer must fit a JSON schema that has no field for them, and the patch is rebuilt from the deterministic text.

The model's answer is validated before anything is used:
- values with quotes or line breaks are rejected;
- numbers the code does not show are rejected;
- a renamed scenario must keep a content word of the original name.

The proposal is redacted before it is sent and is treated as data, never as instructions. Accepted wording is written as a patch in `.ghe/patches/`; the proposal itself is never written. The deterministic run stays the default and the only path in CI.

### Over MCP

`ghk_reverse_scan` and `ghk_reverse_get_evidence` are read-only. `ghk_reverse_propose` writes only `.ghe/reverse/` and needs `mcp.allowWrite`. `accept` is not exposed over MCP ([MCP_GUIDE.md](MCP_GUIDE.md#reverse-engineering-over-mcp-beta)).

## 3. How a proposal is built

```
analyzers ─► Source Evidence IR ─► behaviour candidates ─► proposal (.feature)
                                                              │
                                   parser + IR builder ◄──────┘  (round trip)
                                   lint                ◄──────┘
```

1. **Evidence.** Each fact found is stored with its kind, file and line, the analyzer that found it, a confidence level, and the endpoint it belongs to.
2. **Candidates.** Each endpoint becomes one operation. When several analyzers find the same method and path (for example the code and the OpenAPI document), they are merged into one.
   - The aggregate comes from the controller (`OrdersController` → `Order`) or from the first business segment of the path.
   - The operation name comes from the `operationId`, from a handler whose name starts with a verb, or from the method and path: `POST /orders/{id}/cancel` → `CancelOrder`, `GET /orders` → `ListOrders`.
3. **Scenarios.** Each operation gets one success scenario and one failure scenario per business condition.
   - The success scenario's outcomes are the success status, the state written and the events published.
   - Failures are grouped as validation, authorization, not found, conflict and so on.
   - A precondition on a state (`order.status !== 'PENDING'`) becomes `Given an order with status "PENDING"`, plus a failure scenario for every other state.
   - Technical conditions (5xx, infrastructure) never become scenarios. They are listed as open questions.
4. **Proposal.** One feature per aggregate, tagged `@reverse-engineered @characterization @needs-review` and `@aggregate:<Name>`. Each scenario carries `@command:<Name>` (or `@query:<Name>`) and `@confidence:<level>`. Each scenario and step is preceded by `# evidence: <id> <file>:<line>`.
5. **Verification.** Each proposal is parsed back with the same parser and IR builder that `ghk lint` uses.
   - The IR must recover every declared command; this is the *round trip*.
   - The proposal is linted against `--threshold` (80 by default).
   - Either failure exits 4.

Example, from `tests/fixtures/golden/brownfield-express`:

```gherkin
  # evidence: ev-413df19c26 docs/openapi.json:6, ev-5447a09463 src/orders.js:7
  @command:PlaceOrder @confidence:confirmed
  Scenario: Place an order
    # evidence: ev-89f5042e76 src/orders.js:8
    Given a signed-in user
    # evidence: ev-413df19c26 docs/openapi.json:6, ev-5447a09463 src/orders.js:7
    When the user places an order
    # evidence: ev-58c8dc921b src/orders.js:12, ev-9b745a2483 docs/openapi.json:6
    Then the order is placed
    # evidence: ev-ae1b8df8c8 src/orders.js:10
    And the order status is "PENDING"
```

## 4. Confidence

| Level | Meaning |
|---|---|
| `confirmed` | A test exercises the endpoint, or the code and an explicit contract (OpenAPI) agree |
| `strong` | Read directly from the syntax tree and resolved |
| `inferred` | Deduced from conventions, for example NestJS returns 201 for a POST without `@HttpCode` |
| `unknown` | Not enough evidence. It is written to `unresolved-questions.json` and never becomes a step |

These levels are not percentages: no data set has calibrated them yet. `propose --min-confidence strong` leaves out the scenarios below that level and reports how many were dropped.

## 5. Files it writes

Everything goes in `.ghe/reverse/`. That directory contains a `.gitignore` of `*`, so `git status` never shows it.

| File | Content |
|---|---|
| `scan.json` | Analyzers that ran, with their maturity and evidence count; counts by kind; every evidence item |
| `candidates.json` | One behaviour candidate per operation: aggregate, command or query, scenarios, and the evidence of every step |
| `unresolved-questions.json` | What the code does not answer: endpoints with no observable outcome, technical conditions left out, two endpoints mapped to one name |
| `proposals/<aggregate>.feature` | The proposals. Proposals that a later run no longer produces are removed |

`reverse scan --json` and `reverse propose --json` print the same data as one JSON document. With the global `--dry-run`, both analyse and report but write nothing, not even `.ghe/reverse/`.

## 6. Guarantees

These are tested by `tests/core/reverse.test.ts` and the golden `tests/golden/reverse.test.ts`:

- **Deterministic.** Two runs on the same tree produce byte-identical files. Evidence ids are hashes of what was found and where.
- **No `Then` without evidence.** Every outcome step is backed by evidence that exists in `scan.json`.
- **No invented data.** Quoted values in steps come from the code (status values, messages, roles, event names).
- **Read-only for the repository.** `scan` and `propose` write only to `.ghe/reverse/`; `git status` stays clean.
- **Secrets are never read.** A `.env` next to the code is counted in `secretsSkipped` and its content never appears in any output.

### Round trip

`scripts/reverse-roundtrip.js` measures the analyzers against projects generated by gherkin-ai. For each project it compares the model the generator built from `features/*.feature` (aggregate, commands and the event each one records) with the model `reverse` recovers from the code, and reports precision, recall and F1. Wording is not compared. The projects are analysed in place and nothing is written.

```bash
npm run build && node scripts/reverse-roundtrip.js --json roundtrip.json ../ghk-test-projects/*/
```

On the 16 reference projects (C#, Java, Kotlin, Quarkus, NestJS, Express, Django, Go, Laravel, Rails and Phoenix), the F1 is 1.00 on every project. Each of those projects has one command, so this result shows that the kernel is read correctly in every language. It does not measure analysis of hand-written code; the fixtures and the LMS do that.

On hand-written code that grew away from its features, the F1 against the features is low, and that is expected: it mostly measures how far the code drifted from them. On the LMS (Spring services implemented by hand over the kernel), events are recovered almost completely, because their names are literal in the code. Commands differ wherever the code chose its own names: the feature says `CreateAcademicPeriod`, while the code exposes `POST /periods` and `POST /periods/{id}/open`. That difference is what a review of the proposals is for.

### Spring Boot and Quarkus

| Area | Spring Boot | Quarkus (JAX-RS) |
|---|---|---|
| Routes | `@RequestMapping` on the class, plus `@GetMapping` / `@PostMapping` / … or `@RequestMapping(method = …)` on the method | `@Path` on the class and method, plus `@GET` / `@POST` / … |
| Security | `@PreAuthorize("hasRole('X')")` and `@Secured`, giving 403 with the role | `@RolesAllowed` (403 with the role); `@Authenticated` (401) |
| Input | The `@RequestBody` parameter's class, record or Kotlin data class, with its Bean Validation annotations | The entity parameter, read the same way |
| Failure status | `HttpStatus.*`, `.status(404)`, `ResponseEntity.notFound()`, `@ResponseStatus` on the exception class, `@ExceptionHandler` | `Response.Status.*`, an `ExceptionMapper<X>`, and the built-in exceptions (`NotFoundException`, …) |

Common to both:
- If nothing above gives the failure status, it comes from the exception's name (`…NotFound…` → 404, `…AlreadyExists…` → 409).
- **Calls are followed three levels deep:**
  - into injected services, through the field's or constructor parameter's type (an interface resolves to its implementation);
  - into static factories of project classes (`Course.create(…)`);
  - into methods on loaded entities (`period.open()`), when exactly one project class declares a method of that name.
- **Events** are read from:
  - an event class (`new OrderPlacedEvent(…)`);
  - a generic class named by its first argument (`new DomainEvent("OrderPlaced", …)`);
  - an event-type enum (`OrderEventType.OrderPlaced`);
  - a topic (`kafkaTemplate.send("orders.placed", …)`).

### Lint on proposals

GHK007 (implementation leakage) flags some business words that are also code words. One example is the GDPR *data controller*: a proposal about "the controller terms" scores lower even though its wording is correct. The rule is unchanged, so reword the proposal or disable GHK007 for that feature.

### Validation on open-source code

Every beta analyzer has been run on code gherkin-ai did not write. Spring was checked against the LMS. ASP.NET Core, FastAPI and Go were checked against open-source implementations of the [RealWorld (Conduit) API](https://realworld-docs.netlify.app/specifications/backend/endpoints/), whose specification fixes the 19 expected endpoints. The repositories and their pinned commits are in `tests/fixtures/reverse/oss/realworld.json`. `scripts/reverse-oss.js` fetches them into a cache outside the repository and compares the endpoints `reverse` finds with the specification. The comparison ignores the `/api` prefix, normalises parameter names and leaves out infrastructure endpoints, as the proposals do.

```bash
npm run build && node scripts/reverse-oss.js --json reverse-oss.json   # exit 1 when an analyzer is below F1 0.80
```

| Analyzer | Repository | Endpoints found | Precision | Recall | F1 | Aggregates proposed | Lowest lint score of the proposals |
|---|---|---|---|---|---|---|---|
| `csharp/aspnet` | gothinkster/aspnetcore-realworld-example-app | 19/19 | 1.00 | 1.00 | 1.00 | Article, Comment, Profile, Tag, User | 74 |
| `python/fastapi` | nsidnev/fastapi-realworld-example-app | 19/19 | 1.00 | 1.00 | 1.00 | Article, Comment, Profile, Tag, User | 79 |
| `go/http` | gothinkster/golang-gin-realworld-example-app | 19/19 | 1.00 | 1.00 | 1.00 | Article, Comment, Profile, Tag, User | 69 |

The [golden-build dashboard](https://fennereduardo.github.io/gherkin-ai-cli/goldens.html#reverse) shows these scores. The Pages workflow reruns this validation on every build. The round trips on the reference projects and the LMS need repositories CI does not have, so they come from the release snapshot `docs/reverse-scores.json` (`scripts/reverse-scores.js`).

The table measures route extraction, not the quality of the proposals. Their lint scores (69–79) are below the default threshold of 80: they are drafts to review, as the `@needs-review` tag says. The Go app registers its routes on gin groups that `main` hands to registration functions in other packages. Before 3.3.0 the analyzer lost those prefixes, and the run above found the problem.

### ASP.NET Core, FastAPI and Go

| | ASP.NET Core | FastAPI | Go |
|---|---|---|---|
| Routes | `[Route]` + `[HttpGet]`/…, with `[controller]`/`[action]` tokens; `app.MapGet`/… with `MapGroup` prefixes | `@router.get`/… with the `APIRouter(prefix=…)` and `include_router(prefix=…)` | chi `r.Get`/…, `r.Route("/x", …)`; gin/echo `GET`/… and `Group("/x")`, also when the group is handed to a registration function in another package (`users.Register(v1.Group("/users"))`); a route registered twice (`""` and `"/"`) is one endpoint; `mux.HandleFunc("POST /x/{id}", …)` |
| Security | `[Authorize]` (401), `Roles =` / `Policy =` (403), `[AllowAnonymous]`, `.RequireAuthorization()` | `Depends(...)` / `Security(...)` on an auth dependency (401); a role argument (403) | auth middleware in the group: `r.Use(...)`, `.With(...)`, `group.Use(...)` |
| Input | `[FromBody]` (or complex) parameter; DataAnnotations | Pydantic model; `EmailStr`, `Field(..., min_length=…, gt=…)` | the struct decoded or bound; `validate:"…"` tags |
| Failure status | `NotFound()`, `Results.Conflict(…)`, `StatusCode(…)`, `StatusCodes.Status404NotFound`, `Problem(statusCode: …)`; exceptions by name or by a `Map<TException>` | `HTTPException(status_code=…)`, `status.HTTP_404_NOT_FOUND`, `JSONResponse(status_code=…)`; exceptions by name | `http.Error(w, …, http.StatusNotFound)`, `c.JSON(409, …)`, `echo.NewHTTPError(…)`. A sentinel error (`errors.Is(err, ErrNotPending)`) is linked to the service condition that returns it, so state guards are recovered |
| Calls followed | injected fields, through the class that implements the field's interface | project functions (`services.cancel_order(…)`) | methods with a unique name across the project |

A state violation (`InvalidOperationException`, `IllegalStateException`) is read as 409.

Java, Kotlin, C#, Python and Go are parsed with tree-sitter (`web-tree-sitter` 0.25.10 and five grammars vendored in `vendor/tree-sitter/`; origin and licenses are in its NOTICE.md). They are loaded only when `ghk reverse` reads a file in one of those languages. They add 0.8 MB to the published package (2.7 MB packed, 15.5 MB unpacked).

## 8. Limits

- **Code shows structure, not intent.** A proposal describes what the system does today, including its bugs, and the `@characterization` tag says so. Whether that behaviour is correct is a product decision.
- **Static analysis only.** Reflection, dynamic routing and dependency injection that the type checker cannot resolve are missed. Such endpoints show up with fewer outcomes or as open questions.
- **Data shapes are not specified.** Request and response bodies appear as fields in the evidence, not as data tables in the scenarios.
- **No language model by default.** Wording is template-based; `--assist` is the opt-in wording pass. It has been verified against a simulated provider, and a run against a real model is part of the 3.3.0 release checks.
